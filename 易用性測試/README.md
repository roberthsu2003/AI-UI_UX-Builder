# 易用性測試：讓真實使用者告訴你哪裡不好用 🧪

到了這個單元，你已經有了 Persona、任務流程、`DESIGN.md` 和 Figma 定稿的原型。看起來一切都很完美——但那是 **你** 覺得完美。

設計者對自己的作品太熟悉了，永遠看不出「第一次來的人」會卡在哪裡。**易用性測試（Usability Testing）** 就是請真實使用者實際操作原型，觀察他們在哪裡猶豫、點錯、放棄。

> [!IMPORTANT]
> **只要 5 個人，就能找出大部分的問題。**
> 尼爾森諾曼集團（Nielsen Norman Group）的研究指出，**測試 5 位使用者就能發現大部分的易用性問題**。與其一次找 20 個人，不如每次找 5 個人、修改、再測一次。
> 易用性測試不需要實驗室或昂貴的設備，一支手機、一個原型、一位願意幫忙的同事就能開始。

## 1. 易用性測試是什麼？不是什麼？

| 易用性測試 **是** | 易用性測試 **不是** |
| :--- | :--- |
| 觀察使用者 **做** 了什麼 | 詢問使用者 **喜不喜歡** |
| 給使用者具體任務，看他能不能完成 | 讓使用者隨便逛逛 |
| 找出設計的問題 | 測試使用者的能力 |
| 少量受測者、多次反覆 | 一次找很多人做大型問卷 |

> [!WARNING]
> **使用者說的和做的常常不一樣。** 受測者可能一邊說「很好用啊」，一邊花了三分鐘找不到申請按鈕。請相信你 **觀察到的行為**，而不是受測者的客氣話。

### 和單元 1「網站評估」的差別

| | 單元 1：AI 啟發式評估 | 單元 9：易用性測試 |
| :--- | :--- | :--- |
| 誰來評估 | AI（依據尼爾森十大原則） | 真實使用者 |
| 能找到的問題 | 違反設計原則的地方 | 使用者實際卡住的地方 |
| 優點 | 快速、便宜、隨時能做 | 真實、能發現原則之外的問題 |
| 適合時機 | 改版前診斷舊網站 | 原型完成後驗證新設計 |

兩者是互補的：**先用 AI 評估掃掉明顯的問題，再用真人測試找出真正的痛點。**

## 2. 準備測試：任務腳本與受測者

### 好的測試任務長什麼樣子？

任務必須 **具體、真實、不洩漏答案**。

| ❌ 不好的任務 | 問題 | ✅ 好的任務 |
| :--- | :--- | :--- |
| 「請點擊『線上申辦』按鈕」 | 直接告訴受測者要點哪裡 | 「你想幫 2 歲的孩子申請托育補助，請試著完成申請。」 |
| 「請看看這個網站」 | 沒有目標，無法判斷成功 | 「請找出申請補助需要準備哪些文件。」 |
| 「你覺得首頁好看嗎？」 | 問的是喜好，不是操作 | 「請找出這個月的親子活動，並報名其中一場。」 |

> [!TIP]
> 任務直接取自 [定義使用者與需求](../定義使用者與需求/README.md) 的 **核心任務** 與 **任務流程**。每次測試準備 **3～5 個任務** 就夠了。

### 找受測者

* 盡量找 **符合 Persona** 的人：測長輩用的網站，就不要只找年輕同事。
* **不要找參與設計的人**：他們已經知道答案了。
* 3～5 位就好，可以是朋友的家人、其他部門的同事、課堂上其他組的同學。

### 實作 8-1：請 AI 撰寫測試腳本

```text
我要對 [網站名稱] 的新版原型進行易用性測試。
附件是 persona.md 與 user-flow.md。

請幫我撰寫一份 test-script.md，包含：
1. 開場說明（約 1 分鐘的口白）：說明「我們測試的是網站，不是測試你」、
   請受測者邊操作邊說出想法、可以隨時停止。
2. 暖身問題 2～3 題：了解受測者平常的上網習慣。
3. 測試任務 4 個：用情境描述，不能出現介面上的按鈕名稱或選單名稱；
   每個任務註明「成功的定義」與「預期的操作路徑」。
4. 每個任務完成後的追問：「這個任務有多容易？請用 1～7 分評分」。
5. 結束訪談 3 題：整體印象、最困擾的地方、最喜歡的地方。
```

## 3. 執行測試：放聲思考法與觀察紀錄

### 放聲思考法（Think Aloud）

請受測者 **一邊操作、一邊把心裡想的說出來**：「我在找……這個按鈕應該是……咦，怎麼跑到這裡？」這是了解使用者想法最直接的方法。

### 主持人的三個原則

1. **不要幫忙**：受測者卡住時，忍住不要指給他看。可以說「如果你在家裡遇到這個狀況，你會怎麼做？」
2. **不要解釋**：不要說「這個按鈕其實是……」，你的解釋就是設計的失敗。
3. **用問題回應問題**：受測者問「我應該點這個嗎？」，回答「你覺得呢？」

### 角色分工

| 角色 | 工作 |
| :--- | :--- |
| **主持人** | 唸腳本、引導受測者、追問 |
| **記錄員** | 記下受測者的行為、說的話、卡住的時間點 |
| **（選用）錄影** | 經受測者同意後錄下螢幕與聲音，事後可回看 |

> [!WARNING]
> **錄影與記錄前一定要取得受測者同意**，紀錄中不要寫真實姓名，用「受測者 A、B、C」代替。

### 實作 8-3：觀察紀錄表

請記錄員使用以下表格，每位受測者一份：

```markdown
## 受測者 A（符合 Persona：王怡君 / 38 歲 / 主要用手機）

| 任務 | 完成？ | 花費時間 | 容易度(1-7) | 觀察到的行為 | 受測者說的話 |
| :--- | :---: | :---: | :---: | :--- | :--- |
| 1. 找申請資格 | ✅ | 45 秒 | 6 | 直接點首頁大按鈕 | 「這個很清楚」 |
| 2. 準備文件 | ⚠️ 需提示 | 2 分 30 秒 | 3 | 在 FAQ 和說明頁來回切換 3 次 | 「文件清單到底在哪裡？」 |
| 3. 送出申請 | ❌ 放棄 | 3 分鐘 | 1 | 上傳檔案後不知道有沒有成功 | 「它到底傳上去了沒？」 |
```

## 4. 測量指標：用數字說話

易用性測試主要是質化的觀察，但加上幾個簡單的數字，就能讓報告更有說服力，也能比較改版前後的差異。

| 指標 | 計算方式 | 怎麼解讀 |
| :--- | :--- | :--- |
| **任務成功率** | 成功完成的人數 ÷ 總人數 | 核心任務最好達到 80% 以上 |
| **任務時間** | 從開始到完成的秒數 | 和預期時間比較；第二輪測試應該縮短 |
| **錯誤次數** | 點錯、走錯路徑的次數 | 錯誤集中的地方就是設計問題 |
| **單題容易度（SEQ）** | 每個任務後請受測者評 1～7 分 | 平均低於 5 分的任務需要優先改善 |

> [!NOTE]
> 5 個人的數字 **不具統計意義**，不能說「本網站成功率 80%」。數字的用途是 **找出問題、比較前後兩版**，而不是當作正式的績效指標。

## 5. 分析結果：嚴重度分級與改善優先順序

### 嚴重度分級

測試完會得到一長串問題，不可能全部一次修完。用尼爾森的 **嚴重度分級** 排出優先順序：

| 等級 | 名稱 | 說明 | 處理方式 |
| :---: | :--- | :--- | :--- |
| **4** | 災難 | 使用者無法完成任務 | 上線前一定要修 |
| **3** | 嚴重 | 使用者很吃力才能完成，或多數人都遇到 | 優先修正 |
| **2** | 輕微 | 使用者會猶豫一下，但能自己解決 | 有空就修 |
| **1** | 外觀 | 只影響觀感，不影響操作 | 可以之後再處理 |

### 實作 8-4：請 AI 整理測試報告

```text
附件是 5 位受測者的觀察紀錄（observation-notes.md）。
請幫我整理成易用性測試報告 usability-report.md：

1. 計算每個任務的成功率、平均時間、平均容易度。
2. 把所有觀察到的問題整理成清單，合併相同的問題，並註明有幾位受測者遇到。
3. 為每個問題標示嚴重度（0～4），並說明理由。
4. 每個問題提出改善建議，並註明應該修改的地方：
   - 如果是「規範」的問題（例如按鈕不夠明顯、顏色語意混亂）→ 建議修改 DESIGN.md 的哪一段
   - 如果是「版面或流程」的問題 → 建議修改 Figma 稿或 user-flow.md 的哪一步
5. 最後列出「上線前必修」的前三名。
請只根據紀錄中的內容分析，不要推測紀錄沒有提到的問題。
```

### 實作 8-5：修改後再測一次

易用性測試的價值在於 **反覆**：

```text
測試 → 找出問題 → 修改 DESIGN.md / Figma → 再測試（換 3～5 位新的受測者）
```

修改規範時，記得在 `DESIGN.md` 的 `Changelog` 記下「因為易用性測試發現什麼問題，所以改了什麼」，這就是 [建立自己的 DESIGN.md 實作 2-F](../建立自己的DESIGN_md/02_如何從零建立自己的DESIGN_md.md) 的「稽核 → 修改規範 → 重新生成」循環。

## 6. AI 模擬使用者：測試前的預演

### AI 能扮演使用者嗎？

可以請 AI 扮演 Persona，對著原型截圖或網址「操作」並說出想法。這可以 **在找真人之前先抓出明顯的問題，並檢查測試腳本有沒有寫清楚**。

> [!WARNING]
> **AI 模擬只能當作預演，不能取代真人測試。**
> AI 太聰明、太有耐心，也沒有真實的情緒與生活情境。它會看完畫面上每一個字，而真人只會掃一眼；它不會因為趕時間而放棄，真人會。**AI 沒發現問題，不代表沒有問題。**

### 實作 8-2：AI 預演

```text
請扮演以下這位使用者（附 persona.md 中的主要 Persona），
用他的數位能力、使用情境與心情來操作這個原型（附截圖／網址）。

請依照 test-script.md 中的任務 1～4，逐一：
1. 用第一人稱、放聲思考的口吻說出你看到什麼、想點哪裡、為什麼。
2. 指出你會猶豫或可能點錯的地方。
3. 判斷你能不能完成任務。

最後請以主持人的角度，檢查 test-script.md：
有沒有任務描述洩漏了答案、太模糊，或「成功的定義」不清楚的地方？
```

## 7. 用 Maze 做遠端無主持測試

### 有主持 vs. 無主持

前面介紹的是 **有主持（Moderated）** 測試：主持人在旁邊觀察、追問。另一種是 **無主持（Unmoderated）** 測試：把任務和原型連結發給受測者，讓他們自己在家完成，系統自動記錄點擊路徑、時間與成功率。

| | 有主持測試（本單元 1～5 節） | 無主持測試（Maze） |
| :--- | :--- | :--- |
| 能知道 | **為什麼** 卡住（聽得到想法、可以追問） | **在哪裡** 卡住、多少人卡住 |
| 受測人數 | 3～5 人 | 可以一次發給較多人 |
| 時間成本 | 每人 30～60 分鐘，需要約時間 | 發出連結就好，受測者自己找時間做 |
| 適合 | 第一輪，找出主要問題 | 第二輪，驗證修改後是否改善 |

> [!TIP]
> **兩者搭配最好**：第一輪用有主持測試找出「為什麼」，修改後用 Maze 發給更多人，確認問題真的解決了。

### Maze 是什麼？

**[Maze](https://maze.co/)** 是常見的遠端易用性測試平台，可以直接匯入 **Figma 原型**，設定任務與「預期路徑」，受測者完成後會產生：

* **任務成功率**：直接成功、繞路成功、放棄的比例
* **點擊熱點與路徑**：受測者在每個畫面點了哪裡、走了哪些路
* **誤點率與花費時間**：哪個畫面最讓人困惑
* **問卷與追問**：可以在任務後加入容易度評分（如本單元第 4 節的 SEQ）
* **AI 協助**：Maze 提供 AI 輔助功能，例如協助撰寫追問題目、整理開放式回答（實際功能以官網為準）

### 實作 8-6（選用）：用 Maze 測試 Figma 原型

1. 在 Figma 中確認原型的 **起始畫面** 與 **點擊連結** 都設定好（第 7 單元的定稿原型）。
2. 在 Maze 建立新的測試，選擇 Prototype Test，貼上 Figma 原型的分享連結。
3. 把 `test-script.md` 的任務逐一建立成 Maze 任務，並在原型上點出每個任務的 **預期路徑**。
4. 每個任務後加一題「這個任務有多容易？（1～7 分）」。
5. 先自己預覽跑一次，再把測試連結發給 5～10 位符合 Persona 的受測者。
6. 收到結果後，把 Maze 報告中的成功率、誤點畫面整理進 `usability-report.md`，並和第一輪有主持測試的結果比較。

> [!WARNING]
> * **免費方案每月可做的測試數量有限**，上課前請到 Maze 官網確認目前方案；全班可以分組共用，或由講師示範。
> * 修改 Figma 原型後，Maze 中的連結或預期路徑 **可能需要重新同步或設定**，發出測試前請再預覽一次。
> * 無主持測試看不到受測者的表情、聽不到想法，**數字只告訴你哪裡有問題，不告訴你為什麼**。請和有主持測試搭配使用。
