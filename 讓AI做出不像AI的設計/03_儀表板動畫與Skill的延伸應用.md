# 第三章：延伸應用——儀表板、動畫與 Skill 🚀

[⬅️ 上一章：給足脈絡，並點破 AI 的壞習慣](./02_給足脈絡與點破AI的壞習慣.md) ｜ [🏠 返回單元主頁](./README.md)

同樣的原則（給足脈絡、先探索再製作、點破壞習慣）也能用在網頁以外的產出。本章整理 Nate 示範的三種延伸應用，以及他怎麼把經驗累積下來。本章實作皆為**選做**。

---

## 01. 把資料變成可以即時更新的儀表板

Nate 說 Anthropic 內部大約六到八個月前就不太用現成的儀表板工具了，而是請 Claude 透過 **MCP** 抓資料，寫出剛好符合追蹤需求的儀表板。

他的示範是：

1. 把紐約 MTA 每日運量的大型 CSV 放進 Google Sheets。
2. 給 Claude 連結，只說「把這個做成儀表板」，**連要追什麼都沒指定**。
3. Claude 做完後提醒他：這些數字是試算表的存檔副本，不會自己更新；但因為資料在 Google Drive，可以改成即時讀取。
4. 他同意後，之後每次打開，儀表板就會重新從 Google Sheets 拉資料。

接 BigQuery、Amplitude 這類真實資料源時也是同樣邏輯。

### 數字要能查來源

因為整個儀表板都是程式碼，可以再叫 Claude 做客製視覺化、換不同方式切資料。更重要的是**可以查每個數字的來源**：看 Claude 拉資料用的程式碼（接 Google 的 MCP 時是 JavaScript，接資料庫就是 SQL），懂資料的人可以確認數字真的來自預期的地方。

> [!TIP]
> **一開始不要把需求講太死。** Peter Yang 分享自己請 Claude 分析 YouTube 頻道並研究同類頻道，結果很有洞察。兩人都認為，開放式的需求反而常帶來意外的好結果。資料來源也可以很多元：檔案系統、程式碼、MCP，甚至用排程任務搭配 computer use 去後台抄數字。

> [!NOTE]
> 儀表板常用的圖表框架（Chart.js、D3.js）可以參考 [前端動態框架圖鑑：資料視覺化與捲動互動](../前端動態框架圖鑑/04_資料視覺化與捲動互動.md)。

## 02. 做動畫要照顧人眼的節奏

Nate 一直想讓 Claude 做動態圖像。去年底它勉強做得出來，但爛到好笑；之後每一代模型都進步一點，從「爛到好笑」變成「單純的爛」，再變成「還可以」。他認為現在就在「還可以」的階段，不算出色，但趨勢很明確。

### AI 的弱點：太多東西同時在動

他用同一份 MTA 資料做了一支資料動畫，花了不少時間來回調整。他點出現在模型的一個弱點：**Claude 常讓畫面上很多東西同時變化**。因為它身為機器，可以同時注意很多地方、一次讀大量文字，還沒內化「**人眼很慢，一次只能看一個地方**」這件事。

所以他會提醒 Claude：

* 觀眾需要時間消化，只能專注一處，也讀不快。
* 放文字上畫面時，要想清楚是否**留夠時間讓人讀完**，才出現下一個東西。
* 觀眾的視線，會不會剛好在下一個變化發生的位置？

```text
做這支動畫時請記得：觀眾一次只能看一個地方，而且讀得很慢。
- 同一時間只讓一個主要元素變化
- 每段文字出現後，留足夠時間讓人讀完，再出現下一個東西
- 下一個變化要發生在觀眾視線剛好停留的位置附近
- 整支片要有一條線，一路引導視線
```

其他他給過的回饋包括：「這感覺像靜態投影片，加點動態，讓整支片有一條線一路引導視線。」他也會在走路去吃晚餐時開語音模式，把腦中想像的畫面一股腦講出來，例如選幾個顏色、讓線從某個點開始。講了幾輪之後，作品才到可以微調的程度。

### 用指的比用講的快

最後的微調，他用**註解功能**：直接在影片的某個時間點、畫面某個區域點一下，寫「這段文字重疊了」，不用每次描述「第 17 秒左上角那段文字跟另一段重疊」。標完再跟 Claude 說「我加了一些註解，請處理」。

> [!TIP]
> 工具沒有註解功能時，可以**截圖並圈出問題區域**再貼給 AI，效果類似。這也適用於網頁原型：圈出來，比用文字描述位置快得多。

> [!NOTE]
> [網站架構觀念：設計的講究之處](../網站架構觀念/設計的講究之處/README.md) 提到，一段短動畫往往比一整段文字更快傳達訊息；前提是觀眾來得及看懂。程式化影片可以參考 [前端動態框架圖鑑](../前端動態框架圖鑑/README.md) 介紹的 GSAP 時間軸與 Remotion。

## 03. 把經驗做成 Skill，再用 eval 測

每次反覆調整完，學到的東西要存下來。Nate 有一個專門做 Anthropic 內部風格宣傳短片（sizzle reel）的 [Skill](../Claude網頁設計Skill實戰指南/README.md)，做法是：

1. 把一批官方產品影片放進 Google Drive。
2. 請 Claude 分析影片：看畫格、看每個段落之間停多久，**全部寫下來**。
3. 把分析結果整理成 Skill。

這個 Skill 在內部很受歡迎，大家常用它把一個想法包裝成看起來製作精良的影片，在 Slack 上炒熱氣氛。Nate 說他完全不會 After Effects，所以這對他是全新能力，也讓他體會到不會寫程式的人第一次用 Claude Code 是什麼感覺。

### 用簡單的臨時 eval，避免過度擬合

更新 Skill 時，Peter Yang 擔心會**過度擬合到單一次對話**（只對這次的題目有效）。Nate 的做法是給 Claude 一個 eval 題目：「想出 Claude 最無聊的幾個功能，替它們做宣傳短片。」

每改一次 Skill，就請 Claude 開幾個新的 Claude Code session，**除了 Skill 和一句提示（例如「替模型選單做一支宣傳短片」）什麼都不給**，再看產出內容對不對。這是一種很快的臨時 eval。

這種 eval 他是**自己看結果**，不是另外寫評審模型，因為要寫出評斷好動態設計的 eval，比直接看幾個範例還費工。

### 評分：是非題比一到五分好用

| 評分方式 | 適合用在 | 注意事項 |
| :--- | :--- | :--- |
| **是非題** | 文字有沒有重疊？是不是又用了襯線字體？ | 好寫、好判斷，Nate 認為比一到五分好用 |
| **一到五分** | 需要區分程度時 | 必須具體說明五分長怎樣、四分長怎樣、給一個三分的例子、二分缺了什麼，就像人資部門設計績效考核制度一樣 |

設計品質則很難做 eval。**如果假設模型沒有很好的品味，就不能拿模型去主觀評斷設計好不好。** 能測的是基本的東西：文字有沒有重疊、給十個提示是不是每次都同一個字體和顏色。再深入的好壞，還是要靠人看：讀對話紀錄、看產出、再迭代。

> [!IMPORTANT]
> 這和 [易用性測試](../易用性測試/README.md) 的觀念一致：**AI 可以幫你預演、抓出明顯問題，但「好不好用、好不好看」最後要靠真人判斷。**

## 04. 工作節奏：一條長對話，或一條很短的對話

Nate 有工程背景，以前在 The Browser Company 做 Arc 瀏覽器時就是邊做原型邊驗證，只是當時一個原型要幾週，Arc 推出前光前期製作就花了大約一年。現在在 Anthropic，同樣的事一到兩天就能做完。**沒有被壓縮的，是把東西交到人手上、看他們會不會真的用的那段時間。**

Duet 的開發也是這樣：大家把點子直接做進內部版本，收集同事回饋，快速迭代。做了發現沒解決原本的需求，或以為會很酷但沒人用，就換個方向。Peter Yang 提到，以前寫程式很貴，大家先做很多設計衝刺；現在程式反而是最便宜的部分。

### 怎麼管理對話？

* **大型設計專案：一條對話用到底。** Nate 通常只開一條 Claude Code 對話，讓 Claude 自己開 subagent 處理各種任務。設計新版設計工具時，他在同一條對話裡累積了大約 36 個設計產出，好處是全部共用脈絡，不用擔心某個任務不知道前面發生什麼。他發現 Claude 現在很會處理很長的對話，也會自己管理記憶、脈絡和 subagent。
* **一次性小事：短對話。** 所以他的對話要嘛很短，處理一次性小事；要嘛一條用一個月。
* **在大家本來就在的地方。** Anthropic 內部大量使用 Claude Tag，好處是它就在大家本來就會看訊息的地方。他把 Claude Tag 當成同一個人，而不是很多條對話，直接說「上週我們做的那個東西要改一下，對了它放在哪，幫我找出來」，通常都行得通。

> [!TIP]
> **給課堂的建議**：同一個網站專案的設計探索可以固定在同一條對話（或同一個 Claude 專案）裡進行，讓設計規範、壞習慣清單和選定方向一直留在脈絡中；臨時查資料、問小問題則另開短對話，避免干擾主線。

## 🛠️ 本章實作（選做）

### 實作 3-1：把 CSV 做成儀表板（20 分）

1. 準備一份 CSV（政府資料開放平臺的交通、人口、觀光資料都可以，或專案網站的流量匯出檔）。
2. 只說「把這個做成儀表板」，不指定要追什麼，存成 `dashboard.html`。
3. 追問：「這些數字是怎麼算出來的？請給我計算用的程式碼。」至少檢查一個數字是否正確。

### 實作 3-2：動畫先要分鏡與三種風格（20 分）

1. 請 AI 為你的專案做一支 15 秒的介紹動畫，但**先只要分鏡與 A／B／C 三種風格**，存成 `storyboard.html`。
2. 選定一種風格後才正式製作，並在 Prompt 加上「02. 照顧人眼的節奏」的提醒。
3. 截圖圈出問題（文字重疊、同時太多東西在動），貼回給 AI 修正。

### 實作 3-3：把壞習慣清單做成 Skill，做一次臨時 eval（20 分）

1. 把第二章的 `ai-habits.md` 整理成一個 Skill（做法參考 [Claude Skill 實戰指南](../Claude網頁設計Skill實戰指南/README.md)）。
2. 準備 5 個不同題目（例如：咖啡店官網、牙醫診所、二手書店、社區活動報名、科技新創）。
3. 每個題目**開一個新對話**，只給 Skill 和一句話，生成首頁。
4. 用是非題檢查並記錄：

   | 題目 | 用了襯線字體？ | 米白背景？ | 橘色主色？ | 卡片裝飾色條？ | 文字重疊？ |
   | :--- | :---: | :---: | :---: | :---: | :---: |
   | 咖啡店官網 | | | | | |
   | 牙醫診所 | | | | | |
   | …… | | | | | |

5. 5 個題目的字體與配色是不是都一樣？如果是，回頭修改 Skill，再測一次。
