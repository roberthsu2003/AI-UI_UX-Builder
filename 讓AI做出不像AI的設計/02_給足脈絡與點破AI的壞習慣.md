# 第二章：給足脈絡，並點破 AI 的壞習慣 🧭

[⬅️ 上一章：先發散再收斂——一次要十個方向](./01_先發散再收斂的探索流程.md) ｜ [🏠 返回單元主頁](./README.md) ｜ [➡️ 下一章：延伸應用——儀表板、動畫與 Skill](./03_儀表板動畫與Skill的延伸應用.md)

第一章處理的是「從零開始」。但真實工作裡，大部分時候我們是在**改既有產品**。這一章談兩件事：讓 AI 從真實產品出發，以及直接告訴 AI 它有哪些壞習慣。

---

## 01. 已有產品時，讓 AI 讀程式碼重建畫面

Nate 大部分的工作是改既有產品。這時他不從設計稿開始，而是讓 Claude **直接讀程式碼庫，照程式碼把現在的畫面重建出來**，再在這個基礎上發想變化版本。因為起點就是真實產品，產出自然會長得像這個產品。

他說以前用傳統設計工具時，要花很多時間截圖，再把畫面在設計工具裡重畫一遍，因為真正的權威版本是程式碼。現在這件事交給 Claude 做就好。Claude 以前做得不好，現在已經不錯，而且持續進步。

```text
請讀這個專案裡和〔首頁／結帳流程／會員中心〕相關的程式碼，
先把目前的畫面原樣重建出來（字體、顏色、間距、元件都照程式碼）。
重建完成後，在旁邊並排 3 個變化版本，探索〔改版目標〕。
請保留原版當作對照，不要直接覆蓋。
```

### 不維護長期的設計檔

主持人問到：程式碼改得比設計稿快，設計稿要怎麼保持同步？Nate 的答案是**乾脆不維護長期的設計檔**。每次要設計新東西，就請 Claude 讀程式碼裡相關的部分，重建到畫面上，再從那裡開始設計。他很少回頭更新同一份舊檔。

設計定案之後，如果是他自己要實作，就在同一個對話裡直接說「好，Claude，開始寫吧」。因為這個對話本來就連著程式碼庫，Claude 已經知道要用哪些 CSS 樣式、尺寸、字體、顏色和版面，轉換過程幾乎不會走樣。

> [!NOTE]
> **沒有程式碼庫怎麼辦？** 這個觀念和 [單元 4 主題一](../建立提案用的原型網頁/01_無設計稿的氛圍與視覺探索.md) 用 Google Stitch「數位化重現」舊網站是同一件事：**先重建現況，再發想變化**。沒有程式碼時，可以改用網址、長截圖，或在瀏覽器按右鍵「另存網頁」取得 HTML 交給 AI 讀。

## 02. 直接告訴模型它的壞習慣

AI 做的設計常有一眼就認得出來的破綻。Nate 點出 Claude 最常見的幾個：

| 破綻 | 你會看到的樣子 |
| :--- | :--- |
| **襯線字體** | 標題用優雅的襯線體，不管題目適不適合 |
| **米白色背景** | 偏暖的米色、奶油色底 |
| **橘色** | 主色或強調色是橘色、赭色 |
| **卡片邊緣的裝飾色條** | 卡片左側或上方多一條彩色粗線 |

原因在 [單元主頁](./README.md#-為什麼-ai-做的東西都長一個樣) 說過：模型每次都以為自己是第一次做，**它完全不知道自己有哪些偏好**。

所以團隊發現一個很有用的提示技巧：**直接告訴 Claude 它的失敗模式，以及它容易收斂到哪種風格**。在他們自己的設計工具提示詞裡就寫著，大意是：「這個模型很容易偏向這兩種字體和這兩種顏色，除非使用者要求或真的非常相關，否則不要用。」光這樣就改善很多。

你也可以在自己的 Prompt 裡這樣寫：

```text
提醒你幾個你常見的設計習慣：
- 標題容易用襯線字體
- 背景容易用米白色、奶油色
- 主色容易用橘色
- 卡片邊緣容易加一條裝飾色條
除非我明確要求，或這個品牌真的非常需要，否則請避開以上做法。
請從〔Persona 與品牌〕出發，選擇你平常不會先想到的字體和配色，並說明理由。
```

> [!WARNING]
> **不是叫 AI「反著做」就好。** 只寫「不要用橘色」，AI 可能換成另一個它習慣的顏色。最好同時給**正面的方向**：Persona、品牌既有色、參考網頁。禁止清單是護欄，脈絡才是方向盤。

### 長期解法：建立自己的識別

模型該自己發明全新的設計語言，還是守著一套保守但哪裡都適用的風格？Nate 說團隊也還沒有定論。但**如果使用方法對了，這個問題就不重要**：你會跟 Claude 一起為自己的產品或品牌建立一套識別，或直接帶入既有的品牌規範，模型在沒東西參考時會怎麼發揮，也就不必擔心了。

Peter Yang 的結論是：**個人與品牌的脈絡，才是能帶到下一代模型的長期資產**。這正是下一單元 [建立自己的 `DESIGN.md`](../建立自己的DESIGN_md/README.md) 要做的事。

## 03. 提示不用寫得漂亮，手機筆記和語音都行

Nate 示範了他參與 Claude 個人助理產品 **Duet** 早期發想的例子。當時的想法是讓 Duet 主動提出它能幫忙的事，而且大概要秀出 20 個點子，使用者才會找到一個真的想交出去的任務。

這個點子是他在下班的地鐵月台上想到的：

1. 直接打進 iPhone 備忘錄，寫下一些高層次的想法和例子。
2. 走路回家時，把筆記貼進 Claude Code Remote，接上真實的程式碼庫。
3. 請 Claude **先讀程式碼重建現有畫面，再根據筆記給出這個功能的各種可能樣子**。
4. 隔天早上回到電腦前，畫面上已經有現況重建和好幾種不同方向。

他說這就是他的固定流程：**先從程式碼重建，再要一堆選項，然後往下走**。

### 像坐在後座指揮開車

接下來他用很口語的方式來回修改：

```text
把卡片上的清單做一版更密的，不要副標，允許換行，拿掉分隔線。
加幾個重複性任務的例子。
把圖示對齊格子。
```

Peter Yang 說自己以前會教人寫很詳細的提示，現在越來越懶，提示滿是錯字，人看不太懂，但 Claude 看得懂。Nate 說他最近更常用**語音**，邊走邊碎念，人更看不懂，但這是把想法從腦袋倒出來、邊做邊成形最有效率的方式。

> [!TIP]
> **脈絡要給足，文字不必漂亮。** 這和第一章「塞大量脈絡」並不矛盾：要給的是**資訊**（目的、使用者、參考、喜歡哪個局部），不是修辭。想到就說，比憋到能寫出完美 Prompt 再開始更有效。

### 所有版本都留在畫面上

Nate 還有一個習慣：**請 Claude 改某一版時，讓它複製一份再改**，舊的留著對照。最後也能拿給別人看他探索過哪些方向。

```text
請複製第 3 版再修改，原本的第 3 版保留在畫面上，新版本標示為 3b。
```

這對 Builder 特別有用：提案或發表時能說明「我們試過哪些方向、為什麼放棄」，比只拿出一個最終版更有說服力。

## 🛠️ 本章實作

### 實作 2-1：先重建，再發想（15 分）

1. 準備你選定重構的舊網站：用 Claude Code 開啟網站原始碼，或另存網頁取得 HTML；真的拿不到原始碼時，再改用網址或長截圖。
2. 用「01. 讓 AI 讀程式碼重建畫面」的 Prompt，先重建現況，存成 `rebuild.html`。
3. 在旁邊要 3 個變化版本，並保留原版對照。

### 實作 2-2：寫一份「AI 壞習慣清單」（15 分）

1. 回顧實作 1-1 的 `v0-one-line.html`，加上你和同學觀察到的 AI 味，整理成 `ai-habits.md`：

   ```markdown
   # AI 壞習慣清單

   ## 常見破綻（除非我明確要求，否則避開）
   - 標題襯線字體
   - 米白色背景
   - 橘色主色
   - 卡片邊緣裝飾色條
   - 〔你自己觀察到的〕

   ## 這個專案應該往哪裡走
   - Persona：〔一句話〕
   - 品牌既有色：〔HEX〕
   - 參考網頁：〔網址〕
   ```

2. 開新對話，附上 `ai-habits.md`，用實作 1-1 的同一句話重新生成一次，和 `v0-one-line.html` 並排比較。
3. 記下差異：哪些破綻消失了？有沒有出現新的「習慣」？出現了就補進清單。

> [!IMPORTANT]
> **交付物**：`ai-habits.md`。下一單元會把它併入 `DESIGN.md` 第 7 章「Do's and Don'ts」，讓每次生成都自動帶上這份護欄。
