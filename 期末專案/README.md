# 期末專案：用一個網站，走完整門課 🏁

整門課的每個單元都會產出一份成果。期末專案的設計很簡單：**從第一個單元開始，就選定同一個網站，讓每個單元的產出接力累積**，到最後就是一份完整的改版提案。

```text
選一個「有待優化」的網站
   ↓
評估報告 → 需求文件 → 原型 → DESIGN.md → Figma 定稿 → 測試報告 → 上線網址
```

---

## 🎯 選題建議

| 條件 | 說明 |
| :--- | :--- |
| **真實存在** | 必須是真實上線的網站，才能做評估與比較 |
| **有改善空間** | 資訊繁雜、設計老舊、手機版不好用的網站最適合 |
| **範圍可控** | 不用改整個網站，聚焦在 **首頁＋一個核心任務的流程**（例如：報名、申請、查詢、購買） |
| **找得到使用者** | 能找到 3～5 位符合目標使用者的人來測試 |

> [!TIP]
> 不知道選什麼？可以從 [如何評估現有的網站](../如何評估現有的網站/README.md) 的「推薦評估練習網站名單」挑選，也可以選自己工作單位的網站、學校社團或常去的小店。

## 🎤 期末發表結構

發表時請依照「問題 → 使用者 → 解法 → 驗證」的順序說故事，而不是依照工具的順序：

1. **舊網站的問題**（單元 1、2）：用評估報告與截圖說明最嚴重的三個痛點。
2. **我們為誰改版**（單元 3）：介紹主要 Persona 與情緒最低的旅程階段。
3. **新的設計**（單元 4～8）：展示任務流程、設計規範與最終原型，說明每個設計決策對應哪個痛點。
4. **測試證明它更好用**（單元 9）：報告受測者在哪裡卡住、改了什麼、第二輪的結果。
5. **成果展示**（單元 11）：現場打開公開網址或原型，走一次核心任務。
6. **反思**：AI 在哪些地方幫了大忙？哪些地方 AI 做錯、必須靠人判斷？

> [!IMPORTANT]
> **評分重點不是畫面有多炫，而是「每個設計決策都有根據」。** 能說清楚「因為 Persona 有某個痛點、測試發現某個問題，所以這樣設計」，比用了多厲害的動畫更重要。

## 📊 評分標準

| 面向 | 比重 | 優秀 | 待加強 |
| :--- | :---: | :--- | :--- |
| **問題診斷** | 15% | 評估有截圖佐證，能區分「合理的取捨」與「真正的痛點」 | 只貼 AI 報告，沒有自己的判斷 |
| **使用者與需求** | 20% | Persona 有真實資料支持，任務流程沒有死路，需求有排優先順序 | Persona 完全由 AI 憑空生成，與後續設計無關 |
| **設計一致性** | 20% | `DESIGN.md` 規範清楚，多個頁面風格一致，元件狀態完整 | 頁面之間顏色、按鈕、間距不一致 |
| **易用性驗證** | 25% | 有真人測試紀錄，問題有分級，並依結果實際修改設計 | 沒有測試，或測試後沒有任何修改 |
| **成果與發表** | 20% | 故事清楚、每個設計決策都說得出理由，核心任務能順利示範 | 只展示畫面，說不出為什麼這樣設計 |

> [!NOTE]
> 🅿️ PM 理解版與 🛠️ 動手實作版使用同一份評分標準。PM 理解版的「成果」可以是高保真原型（Stitch、Claude Design 或 Figma 的分享連結），不要求公開網址。
